## Problem
`backend/src/routes/auth.js` (the `/verify` handler, about lines 92-99):

```js
if (!user.email_verified) await checkCode(user.id, body.code);
res.json({ token: signToken(user), user: publicUser(user) });
```

For an account with `email_verified = true`, the code is never checked, and any 6-digit value returns a 30-day JWT for that user. Migration `013_email_verification.sql` adds the column with `DEFAULT true`. That covers every existing, seeded, social and admin-made account, including admins, and with `ADMIN_ENABLED` it reaches the admin API.

Introduced in `cdb36c5` (2026-11-05). Found by reading the code during the learning session; not tested against any server.

## Fix
- [ ] In `/auth/verify`, when `user.email_verified` is already true, refuse (for example the same 400 "Kod je istekao. Traži novi." used for unknown users) instead of issuing a token. Only `checkCode` success may lead to `signToken`.
- [ ] Check the app's code step (`app/lib/screens/auth_screen.dart`, `Session.verifyEmail`) still works: it only calls verify for unconfirmed accounts.
- [ ] Consider rate limiting `/auth/login`, `/auth/verify` and `/auth/verify/resend` (the backend has none today).
- [ ] Deploy to the Coolify beta, then consider rotating `JWT_SECRET` to invalidate any tokens that may have been issued through this path (this logs everyone out).
- [ ] Add a short regression check (curl: verify with a wrong code on a verified account → 4xx).
- [ ] Add an entry to docs/CHANGELOG.md.
